# Release

Every artefact of v0.1 comes from one tag through `.github/workflows/release.yml`:
the Server Host binaries, the distroless image, the Flutter web bundle, the signed
arm64 APK and the unsigned IPA. There is no GHCR image in v0.1.

| Artefact | How it is built | Status |
|---|---|---|
| `parley-server-linux-amd64.tar.gz`, `-linux-arm64`, `-darwin-arm64`, `-windows-amd64` | `CGO_ENABLED=0 go build ./cmd/parley-server` on Ubuntu | Built and run locally |
| `parley-server-<version>-image.tar.gz` | `deploy/Dockerfile` (distroless static, one Go binary), `docker save` | Dockerfile built by ticket 10; the workflow runs and smokes it on every release |
| `parley-<version>-web.tar.gz` | `flutter build web --release --no-web-resources-cdn`, plus the mirrored Noto CJK fallback slices | Built locally; browser smoke, CSP, same-origin and brotli budget enforced in CI; the image embeds it at `/`, bare metal extracts it to `web-app/` |
| `parley-<version>-arm64.apk` | gomobile arm64 AAR + `flutter build apk --release`, signed with the retained v0.0.2 key | Signed locally with that key; certificate checked by the workflow |
| `parley-<version>-unsigned.ipa` | `flutter build ios --release --no-codesign` on `macos-latest` | Workflow only (no macOS host here); first run is PENDING-USER |

## Trigger and tag policy

Tags are **human-gated**: no workflow creates a tag. Push an existing `vX.Y.Z`
tag, or run Actions → **Release** → *Run workflow* for a dry run.

- A tag push builds everything and publishes a GitHub Release.
- A manual run builds everything into the workflow run only (no release) and
  **fails if the tag for the current version already exists** — a dry run must
  not race a human-created tag.
- A tagged run refuses to run when that GitHub Release already exists, so assets
  are never overwritten.
- The macOS IPA job has not been exercised yet; treat the first IPA build as
  unverified until the PENDING-USER check below.

## Versioning

`client/pubspec.yaml` is the only version source, currently `0.1.0+1000`. The
build number must equal `major * 1,000,000 + minor * 1,000 + patch`, so v0.1.0
is versionCode **1000** and stays an in-place upgrade over v0.0.2. The tag must
be `v` + the pubspec version.

`scripts/version.sh` enforces this and prints `version`, `version_code` and
`tag`; `--tag vX.Y.Z` also checks the tag, `--require-tag-absent` implements the
dry-run rule, and `--github-output FILE` feeds the workflow.

CI runs the same check on every change, so a pubspec bump with a hand-written
build number fails before it can reach an APK.

## Android signing

The release APK uses the **retained v0.0.2 signing key**, so it upgrades the
installed app. The certificate SHA-256 is
`eb1f6f0dbcd938b34f8db1ebaeb0ba0304a67b60312bc24b18e6c69d282333e8`
(a public fingerprint, safe to track). `scripts/check-apk.sh` verifies it, the
application id `app.parley.translate`, versionCode 1000 and
`zipalign -c -P 16` (16 KiB page alignment) before the artefact is uploaded.

The four repository secrets are referenced by name only; no value or keystore is
in the repository or printed in logs:

- `ANDROID_KEYSTORE_BASE64` — base64 of the release keystore
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

The workflow decodes the keystore into `$RUNNER_TEMP` (outside the repository),
exports `ANDROID_KEYSTORE_PATH`, and Gradle signs the release build. On a
**tagged** run all four secrets are required: a missing one fails the guard job
with an explicit error. On a **manual** run without secrets the APK is
debug-signed and named `parley-<version>-arm64-debug.apk`, with a workflow
warning.

`client/android/app/build.gradle.kts` reads those four variables; a local build
without them is debug-signed, as before.

## Release notes

The published release body is generated by the workflow and always states the
two upgrade rules:

- **Keys and settings must be re-entered once** after upgrading from v0.0.2.
- **Uninstall any debug-signed Parley build first**; debug and release builds
  use different signing keys, so Android refuses to install one over the other.

The body also lists the artefacts and their SHA-256 sums, and the APK's
certificate fingerprint.

## CI

`.github/workflows/ci.yml` runs on pull requests and branch pushes:

| Job | Checks |
|---|---|
| Version | `scripts/version.sh` — pubspec version, versionCode formula and tag |
| Go | `go vet ./...`, `CGO_ENABLED=0 go test -count=1 ./...` (unit tests, trace replay, Conformance Suite against the in-process Bun oracle), `CGO_ENABLED=0 go build ./...`, no tracked keystore/`.env` |
| Legacy JS oracle | `bun run lint`, `bun run test`, `bun run smoke` — kept until P4 |
| Flutter | `dart format --output=none --set-exit-if-changed`, `flutter analyze`, `flutter test` (widgets, goldens, accessibility guidelines) |
| Web budget | `flutter build web --release --no-web-resources-cdn`, then the brotli budget |
| Android | path-filtered by `scripts/android-changed.sh` (documentation-only diffs skip it): Java 17, NDK r28, pinned gomobile, `gomobile bind -target=android/arm64 -androidapi 24`, `flutter build apk --debug`, `zipalign -c -P 16` and versionCode |

A deliberate trace regression fails the Go job; a deliberate golden change
fails `flutter test`. Both were exercised locally while building this pipeline.
The web budget sums the cold-load set (entry files, `main.dart.js`, one CanvasKit
pair, fonts and the manifest) at brotli quality 11 and fails above 3.5 MiB
(`scripts/web-size-budget.mjs`, override with `WEB_BROTLI_BUDGET_MIB`). Alternate
renderers, debug symbols and the lazily-loaded TTS engine are not cold-load bytes.
